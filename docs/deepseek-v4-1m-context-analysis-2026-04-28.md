## 执行摘要

DeepSeek-V4 开源社区将上下文长度视为类似内存容量的规格指标——Llama 4 1M、Qwen3 256K、GLM 4.5 400K、DeepSeek-V4 1M。但 1M 上下文 ≠ 无损长记忆。

**核心发现：**
- V4 将注意力机制改造为三个并行通道：128:1 全局摘要（HCA）、4:1 稀疏选择（CSA）、128 token 局部保真窗口（SWA）
- KV 缓存压缩至 BF16 GQA8 基线的 2%
- 代价：MRCR 8-needle 准确率从 8K 的 0.94 降至 1M 的 0.59
- 成本比 V3.2 低一个数量级，但仍落后 Claude Opus 4.6 约 10 个百分点（0.93）

---

## 1. 上下文规格的真实含义

开源社区将上下文长度当作独立规格看待——如同 RAM 容量。Llama 4 1M、Qwen3 256K、GLM 4.5 400K、DeepSeek-V4 1M，看起来只是个数字，隐含假设是模型在这么长的上下文上"和短文本一样工作"。

**这是误读。**

闭源前沿实验室（Anthropic、Google）未公开长上下文架构，但当 Claude Opus 4.6 在 1M MRCR 8-needle 上取得 92.9、Gemini 3.1 Pro 取得 92.4 时，可大致推断它们使用接近稠密注意力的方案——为更高检索天花板支付工程成本。

DeepSeek-V4 采取相反路径：**承认注意力在 1M 长度上必然有损**，然后将损失放置在模型最不敏感的位置。

---

## 2. 核心性能数据

| 指标 | V4-Pro vs V3.2 @ 1M | V4-Flash vs V3.2 @ 1M | vs BF16 GQA8 基线 |
|------|---------------------|----------------------|------------------|
| 单 token 推理 FLOPs | 降至 27% | 降至 10% | - |
| KV 缓存 | 降至 10% | 降至 7% | ≈ 2% |

**三个关键脚注：**

1. **比较基线是 V3.2，而非原版注意力** — V3.2 已集成 DSA，V4 是在已稀疏化基线上再压缩一个数量级
2. **"FP4 × FP8 的 1/3 加速"是未来硬件选项** — 在 H100/H200/B200 上 FP4×FP8 与 FP8×FP8 峰值 FLOPs 相同，论文措辞为"理论上在未来硬件上可提升 1/3"
3. **"2% KV 缓存"是四层压缩的乘积** — 序列维度压缩 + K/V 共享 + BF16→FP8 + Indexer KV FP4

## 3. 架构核心：三车道并行注意力

V4 的每层注意力（除前两层外）是一个**三车道并行结构**。每个查询同时访问三个信息通道：

### 3.1 HCA（全局摘要车道）
- **压缩比**：m' = 128
- **机制**：1M token 压缩为 ~7,812 条目，每条目是 128 个原始 token 的有损摘要
- **特点**：覆盖全部 1M（全局），但每个点严重损失精度

### 3.2 CSA（稀疏精确读取车道）
- **压缩比**：m = 4
- **机制**：1M token 压缩为 ~25 万 4-token 块；Lightning Indexer 评分后仅让查询关注 top-k=1024 最相关条目
- **特点**：覆盖全部 1M，但实际只读取 ~0.4%

### 3.3 SWA（局部保真车道）
- **机制**：最近 128 个 token 的 K/V 保持完整保真，无压缩
- **特点**：仅最近 128 token，但完全保留

**查询实际"看到"的信息预算：**

| 车道 | 高保真比特数 | 说明 |
|------|-------------|------|
| SWA | 128 token 当量 | 100% 保真局部上下文 |
| CSA | 1,024 × 4 = 4,096 token 当量 | 4:1 有损，由 Indexer 挑选的精确读取区域 |
| HCA | 7,812 × 128 = 完整 1M token | 128:1 有损全局氛围 |
| **总计** | ≈ 4,224 高保真 + 1M 低保真 | "稀疏精确读取 + 模糊全局视图" |

---

## 4. CSA（压缩稀疏注意力）详解

### 4.1 两步设计

**第一步 — 压缩**：每 m=4 个连续 token 的隐藏状态用学习 softmax 权重压缩为 1 个 KV 条目。1M token → 25 万条目。

**第二步 — 稀疏选择**：独立 Lightning Indexer 评分全部 25 万条目；查询仅关注 top-k=1024。

### 4.2 Lightning Indexer

继承自 V3.2 的独立注意力子网络，仅用于评分：
- 独立 indexer KV（每 4 token 一个，head dim 仅 128）
- FP4 点积 — 比主注意力的 FP8 更便宜
- ReLU 激活后接 top-k

**核心风险**：Indexer 的排序质量决定主注意力的上限。若 indexer 将真正相关条目排在第 1100 位，top-k=1024 的查询永远不会看到它。

### 4.3 重叠压缩（Overlap Compression）

V4 对 CSA 的真正创新：同时生成两组 KV（C^a, C^b），覆盖交错的 4-token 块，然后跨块 softmax。

- **收益**：缓解"块边界信息断裂"问题
- **成本**：预压缩 KV 内存翻倍，CSA 层参数量翻倍

---

## 5. HCA（重度压缩注意力）详解

### 5.1 反直觉设计选择

| 维度 | CSA | HCA |
|------|-----|-----|
| 压缩比 | m = 4 | m' = 128 |
| 压缩风格 | 重叠（两套 KV）| 非重叠（单套 KV）|
| 稀疏选择？| 是（top-k=1024）| 否，全稠密 |
| Indexer 需要？| 是 | 否 |
| 每条目压缩 token 数 | 4 | 128 |

**为何 HCA 敢"压缩后全稠密"？**

m'=128 压缩后，1M token 缩减为 1,000,000 / 128 ≈ 7,812 条目。7,812 KV 在稠密注意力预算内 — 相当于 8K 上下文上的稠密注意力。

**核心权衡**："以极端压缩换取消除稀疏选择复杂度"

### 5.2 信息密度极限

m'=128 意味着每个压缩条目必须将 128 个原始 token 的语义塞入 c=512 维向量。原始隐藏状态 d=4096~7168 维，128 token × 7168 dim = ~91.7万维信息 → 压缩至 512 维。**压缩比 1800:1**。

这是 V4 架构中最有损的阶段。HCA 条目注定只能捕捉"全局氛围"而非"具体事实"。

---

## 6. SWA（滑动窗口注意力）

### 6.1 补丁式设计

纯 CSA + HCA 的问题：因果性要求查询不能关注自身压缩块（否则会泄露未来 token 信息）。这意味着包括查询本身在内的最近一段 token 对 CSA 和 HCA 都不可见。

但在语言建模中，**最近几个 token 恰恰是下一个 token 预测的最关键信号**。

**解决方案**：添加第三车道 SWA，查询额外关注最近 n_win = 128 个未压缩 token 的 K/V。

### 6.2 设计细节：n_win = m' = 128

这两个数字相等非偶然 — SWA 窗口大小恰好等于 HCA 压缩比。SWA 覆盖的范围正是"当前 HCA 块"的范围。

**三车道严格互补分工：**
- **SWA**：最近 128 token（当前 HCA 块范围）
- **HCA**：所有更早的压缩 HCA 块（开头 → ~当前-128）
- **CSA**：从全部 4-token 压缩块中挑 top-k=1024，无位置限制

## 7. 关键工程技巧

### 7.1 注意力 Sink（Softmax 温度控制）

来自 StreamingLLM 的技巧：每个注意力头添加可学习标量 z'_h 到 softmax 分母。

**结果**：注意力权重不必和为 1，可以是 0.7、0.3 或接近 0。

**意义**：在稀疏注意力下，若 CSA 的 top-k=1024 选中条目都不相关，无 sink 时 softmax 会强制注意力均匀分散在 1024 个不相关条目上，产生巨大噪声。有 sink 时，模型可以学习"我不在乎这 1024 个 — 让注意力全流向 sink"，该层输出几乎不受影响。

> **Sink 的真正含义**：给注意力层提供合法退出当前层的选择。无 sink 时，稀疏注意力失效模式是静默输出错误信号；有 sink 时，失效模式变为输出接近零信号，让下一层恢复。前者是静默损坏，后者是优雅降级。

### 7.2 逆 RoPE（Inverse RoPE）

V4 在 CSA/HCA 使用部分 RoPE — 仅对 query 和 KV 向量的最后 64 维应用 RoPE，其余位置无关。

**问题**：CSA/HCA 的 KV 是 K=V 共享（MQA 风格）；注意力输出是 Σ s_j × V_j。若 V_j 的最后 64 维携带绝对位置编码（位置 j），则 Σ s_j × V_j 混合不同位置的 RoPE 成"位置的加权和" — 既非绝对也非相对，基本是噪声。

**V4 解法**：输出侧用位置 = -i 的 RoPE 旋转注意力输出。这使得输出的"有效位置"变成 j - i = -dist，每个 V_j 对输出的贡献被查询-键距离重新编码，自动转换为相对位置编码。

## 8. 性能数据深度解读

### 8.1 MRCR 8-needle 准确率曲线

| 上下文长度 | 8K | 16K | 32K | 64K | 128K | 256K | 512K | 1024K |
|-----------|-----|-----|-----|-----|------|------|------|-------|
| V4-Pro-Max | 0.90 | 0.85 | 0.94 | 0.90 | 0.92 | 0.82 | 0.66 | 0.59 |
| V4-Flash-Max | 0.91 | 0.84 | 0.87 | 0.85 | 0.87 | 0.76 | 0.60 | 0.49 |

**对比前沿模型 1M MRCR 8-needle：**
- Claude Opus 4.6: 0.929
- Gemini 3.1 Pro: ~0.92
- V4-Pro-Max: 0.835

**关键事实：**

1. **128K 内 V4-Pro 接近前沿**（0.92 vs 0.93）。1M 才是真正出现分化的位置 — V4 落后 Claude 9-10 个绝对百分点。
2. **V4-Pro 1M（0.59）优于 V4-Flash（0.49）** — 更大总参数量 + 更大 top-k（1024 vs 512）直接帮助长上下文检索。
3. **0.59 @ 1M 比 8K 的 0.90 低 34 个百分点** — 这就是"1M 上下文质量成本"的具体数字。

### 8.2 异常数据：1M 得分高于 128K？

| 模型 | MRCR 8-needle 128K | MRCR 8-needle 1M |
|------|---------------------|------------------|
| V4-Pro-Max | 78.6 | 83.5 |
| V4-Pro | 78.4 | 81.0 |

这与图 9 的单调递减趋势矛盾。**猜测：**
1. 训练分布：V4 后期长上下文训练集中在 1M 周围；128K 只是训练计划中的"中转点"
2. HCA 甜蜜点：1M 序列在 m'=128 压缩下产生 7,812 稠密条目 — 恰好是 HCA 设计最优值。128K 序列仅产生 1,000 条目，太稀疏

**启示**：V4 的长上下文能力是"为 1M 训练"，而非"跨长度通用"。若真实工作负载在 200K~500K，可能未命中论文强调的甜蜜点。

## 9. 设计总结

**前 10 节压缩为一句话：**

> V4 的注意力不是注意力 — 而是"有损压缩 + 稀疏检索 + 局部保真 + 显式弃权"的复合检索系统。每层中查询同时咨询三种粒度视图（SWA 局部、CSA 精确、HCA 全局），依赖 indexer 的排序质量、sink 的"放弃"机制、部分 RoPE 的位置耦合，将"看似不可能的 1M"工程化为"可日常服务的 1M"。

**该设计的真实定位**：不是"创新"，而是工程级组装已有、独立验证的组件：
- Lightning Indexer + top-k: V3.2 DSA
- Latent query / 低秩 K=V 共享: V2 MLA
- 部分 RoPE: V2 延续
- 滑动窗口: Mistral / Gemma 主流
- Attention Sink: StreamingLLM, GPT-OSS
- 压缩 + 稠密交错: Native Sparse Attention 谱系

**V4 的真正贡献**：工程组合 + 端到端 1M 可服务性 — 让这些组件在稳定训练的 32T token、1.6T 参数 MoE 中共存，配合定制 KV 缓存管理、稀疏注意力内核、上下文并行训练基础设施。

## 10. 实践指导

### 当开源模型声称 1M 上下文时，应该问：

1. **注意力是否稠密？** 若非稠密，则是**有损 1M**
2. **MRCR 1M 8-needle 分数？** 0.85+ 为前沿级；0.5-0.6 表示"可运行但不适合精确检索"
3. **压缩比多少？** HCA 式 128:1 压缩注定某些精度任务无法完成 — 这不是"更多训练"能修复的

### 设计长上下文应用时：

**适合 V4 的场景：**
- 长文档推理（如 CorpusQA，V4-Pro-Max 33.6 vs Gemini 35.4）— 需要"全局氛围 + 局部细节"而非点对点精确匹配
- 大型代码库分析
- 多文档摘要
- Agent 长轨迹维护

**不适合 V4 的场景：**
- 法律条款检索
- 从医学文献提取具体数字/命名实体
- 长转录稿中引用精确时间戳

**替代方案：** 严格 needle 检索任务使用 Claude Opus 4.6 / Gemini 3.1 Pro，或前置 RAG。

### 架构研究方向：

1. **Indexer's top-k 排序准确率如何消融？** 这是 CSA 天花板的瓶颈
2. **HCA 的 m'=128 是经验最优，还是 m'=64/256 也可行？** 论文未扫这个曲线
3. **三车道间注意力权重分配是学习的 — 某些层 sink 是否已"关闭整个 HCA 车道"？** 若如此，HCA 的实际贡献被高估

## 11. 结语

"1M 上下文"作为规格线已在 2025-2026 开源模型竞赛中被反复刷新。V4 的真正贡献是首次写下对"1M 究竟如何构建"的完整答案 — 不是"我们拓宽了注意力窗口"，而是"我们用五种不同压缩/选择/窗口机制将注意力撕碎，每种处理其最适合的粒度"。

这种透明度值得鼓励。但读者 — 尤其是工程读者 — 需要看到规格数字背后隐藏的架构成本：

- 1M 的 KV 缓存仅 2% 是因为信息已挤过四层压缩
- 1M 的 FLOPs 仅 27% 是因为注意力已从 O(N²) 退化为"分层近似，大致 O(N·log N)"
- 1M 的检索准确率从 8K 的 0.94 滑至 0.59，因为这种近似有精度天花板，且天花板不会被训练数据治愈

下次有人告诉你"1M 上下文模型来了，RAG 已死"，发给他们图 9 的曲线 — 那条从 0.94 降至 0.59 的曲线。

**1M 上下文 ≠ 无损长记忆。**

它是工程权衡的胜利，是诚实的披露：某些任务你仍需要 RAG、仍需要稠密注意力、仍需要其他外部记忆系统。

V4 并未解决长上下文。V4 只是将"长上下文的可服务边界"大幅推进。这已足够。
