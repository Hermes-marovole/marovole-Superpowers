## 执行摘要

2026年4月30日，前字节跳动工程师、连续创业者郭宇（guoyu.eth）在 X 平台分享了对 Stripe 新发布功能的观察：Stripe Treasury 可能成为 harness engineering 的关键基础设施，使得像 wanman 这类 AI Agent 工具不仅能生成创业方案，还能直接开设银行账户并授权 Agent 执行付款。更具前瞻性的是，该功能默认支持加密货币。

本文档将深入解析这三个关键要素——Stripe Treasury、harness engineering 和 wanman AI，探讨它们如何共同构建 AI Agent 时代的财务基础设施。

## 一、原帖核心观点

> "Stripe 今天新发布了一个功能 Treasury，我觉得这会是集成在 harness engineering 中的一个重要产品，让 wanman 这类工具不仅可以做出初创公司的方案，还能直接开设银行账户，并授权 agent 使用这些账户进行付款。有意思的是，它还默认支持 crypto"

### 1.2 关键洞察

| 要素 | 说明 |
|------|------|
| **Stripe Treasury** | Stripe 的银行即服务（BaaS）产品，2020年底推出 |

| **Crypto 支持** | 默认支持加密货币（USDC 等稳定币） |

### 1.3 为什么重要

- **以前**：AI 只能生成商业计划书、财务预算

## 二、Stripe Treasury 深度解析

### 2.1 什么是 Stripe Treasury

Stripe Treasury 是 Stripe 于 2020 年底推出的**银行即服务（Bank-as-a-Service）**产品，与高盛、花旗等持牌银行合作，为平台类客户提供内嵌的金融账户功能。

### 2.2 核心功能

#### 2.2.1 企业版功能

| 功能 | 说明 |
|------|------|
| **简化资金管理** | 在同一管理平台中管理付款和财务，与财务软件无缝集成 |
| **即时获取资金** | 几分钟即可开户，已结算收入即时到账 |
| **无代码打款** | 数分钟内以收款方当地货币完成支付 |
| **API 批量汇款** | 使用灵活的 API 实现大规模批量汇款 |
| **秒级身份验证** | 秒级验证收款人身份，自动关联银行账户详情 |

#### 2.2.2 平台版功能（Treasury for Platforms）

这是与 Harness Engineering 最相关的版本：

```
Stripe Treasury 平台版 = Connect + 嵌入式金融服务
```

**关键能力**：
- **为客户开设金融账户**：SaaS 平台可通过 Stripe 为其商户开立资金账户
- **支持存款和转账**：完整的银行级账户功能
- **ACH 和电汇转账**：完整的支付网络接入
- **FDIC 穿透式存款保险**：资金安全保障
- **模块化组件**：按需组合金融功能

### 2.3 Crypto 支持详情

Stripe 对加密货币的支持是分阶段推进的：

#### 2022年4月
- 重返加密市场，在 Connect 平台推出加密货币代付功能
- 与 Twitter 合作，允许创作者以 USDC 提取收入
- 通过 Polygon 区块链进行低成本支付

#### 2024年4月
- 正式推出"使用加密货币支付"功能
- 支持 USDC 稳定币，覆盖以太坊、Solana、Polygon 三大网络
- 覆盖 150+ 国家
- 手续费：1.5%，单笔上限 1 万美元

#### 2024年10月
- Paxos 推出新稳定币支付平台
- Stripe 持续深化稳定币基础设施

#### 支持的加密货币

| 币种 | 网络 |
|------|------|
| USDC | Ethereum、Solana、Polygon、Base |
| USDT | Ethereum、Solana |

### 2.4 技术实现方式

```
┌─────────────────────────────────────────────────────────┐
│                   平台/应用 (如 Wanman)                    │
│                     ↓ Stripe API                        │
├─────────────────────────────────────────────────────────┤
│                    Stripe Treasury                      │
│                     ↓ 合作银行网络                       │
├─────────────────────────────────────────────────────────┤
│   高盛 │ 花旗 │ Evolve Bank │ 法兰西兴业银行 等...      │
└─────────────────────────────────────────────────────────┘
```

## 三、Harness Engineering 全面解读

### 3.1 核心概念

Harness Engineering（基座工程）是决定 AI Agent 能否真正工作的关键学科。它不仅仅关注模型选择（Claude vs. GPT vs. Gemini），而是将焦点放在包裹模型的"控制环"上。

**核心公式**：
```
智能体 = 模型 + 控制环 (Harness)
```

### 3.2 指南与传感器的分类

Harness 包含两种根本不同的控制类型：

#### 3.2.1 指南（Guides）——前馈控制

在智能体行动之前对其进行引导：

| 类型 | 示例 | 作用 |
|------|------|------|
| 架构文档 | `AGENTS.md`、`CLAUDE.md` | 编码最佳实践 |
| 启动脚本 | 初始化工作上下文 | 注入项目特定知识 |
| 仓库规范 | 代码结构、命名约定 | 主动防止错误输出 |

#### 3.2.2 传感器（Sensors）——反馈控制

观察智能体行为并生成修正信号：

**计算型传感器**（确定性、毫秒级）：
- TypeScript 类型检查器
- ESLint
- 格式化器
- 结构化 Linter

**推断型传感器**（概率性、较慢）：
- AI 代码审查器
- 意图符合度评估
- 语义层面错误检测

### 3.3 金融场景下的 Harness 设计

当 AI Agent 涉及资金操作时，Harness 设计变得更加关键：

#### 3.3.1 风险控制分层

```
Layer 1: 输入验证
  - 提示词注入检测（Prompt Injection）
  - 敏感数据泄露检测
  - 身份验证

Layer 2: 决策控制
  - 规则引擎审查
  - 信用评分验证
  - 交易限额检查

Layer 3: 输出验证
  - 幻觉检测（Perplexity 检测）
  - 合规性检查
  - 人工复核触发

Layer 4: 执行监控
  - 实时风控
  - 异常交易检测
  - 审计日志
```

#### 3.3.2 关键安全机制

| 机制 | 说明 | 金融场景阈值示例 |
|------|------|------------------|
| **提示词注入检测** | 计算输入与已知攻击样本的相似度 | sim > 0.85 判定为疑似注入 |
| **幻觉检测** | 通过 PPL（困惑度）评估输出可信度 | PPL > 30 判定为疑似幻觉 |
| **敏感数据检测** | 识别身份证号、银行卡号等 | 正则匹配 + 模型识别 |
| **信用评分验证** | 验证用户是否有足够信用 | 征信分 < 600 拒绝贷款 |

### 3.4 生成器-评估器分离架构

Anthropic 推荐的模式：

```
用户输入 → 规划器(Planner) → 详细规范
                ↓
           生成器(Generator) → 功能实现
                ↓
           评估器(Evaluator) → 测试验证
                ↓
              交付
```

**评估器职责**：
- 使用 Playwright 进行浏览器交互测试
- 评估设计质量、原创性、工艺和功能
- 与生成器协商"完成"标准

**为什么重要**：
- 避免自我评估的过度自信偏差
- 使评估标准显式化且可检查
- 在编写代码前达成"完成"共识

## 四、Wanman AI：一人公司的未来

### 4.1 项目概述

Wanman（万物）是郭宇正在开发的 AI Agent 项目，愿景是：

> "让世界上所有人，都能在 AI agents 团队的帮助下，从零创办或接管任何组织，围绕用户的核心意图，持续自动化地运营一人公司。"

### 4.2 核心能力

根据郭宇在 X 上的分享，wanman 具备以下特征：

| 能力 | 描述 |
|------|------|
| **CLI 交互** | 用户在命令行中告诉"CEO"要做什么 |
| **全自动执行** | 自动执行多个"工作日"的任务 |
| **Agent 团队** | 每个工作日会"请"新的 agent 员工 |
| **闭环运营** | 持续自动化运营一人公司 |

### 4.3 实际应用案例

#### 案例 1：开咖啡馆
```
用户：帮我在中目黑开一家咖啡馆
```

### 5.2 关键安全机制

在资金场景中，Harness 需要特别强化：

| 层级 | 机制 | 实现方式 |
|------|------|----------|
| **身份层** | 多因素认证 | Stripe Identity + 生物识别 |
| **授权层** | 分级权限 | 只读 → 小额转账 → 大额转账 |
| **风控层** | 实时检测 | Radar 风控引擎 + 自定义规则 |
| **审计层** | 全程留痕 | 不可篡改的审计日志 |
| **恢复层** | 应急机制 | 紧急冻结、人工接管 |

### 5.3 Crypto 的独特价值

默认支持加密货币带来了几个独特优势：

| 优势 | 说明 |
|------|------|
| **全球无障碍** | 跨境支付无需 SWIFT，秒级到账 |
| **低手续费** | 相比传统电汇（$20-50），USDC 转账几乎免费 |
| **24/7 运行** | 不受银行营业时间限制 |
| **Agent 原生** | 区块链地址比银行账户更适合 Agent 操作 |
| **可编程性** | 智能合约实现条件付款、托管等复杂逻辑 |

## 七、风险与挑战

### 7.1 技术风险

| 风险 | 严重性 | 缓解措施 |
|------|--------|----------|
| Agent 幻觉导致错误付款 | 高 | 多重确认、限额控制 |
| 提示词注入攻击 | 高 | 输入验证、 Harness 过滤 |
| 私钥泄露 | 极高 | 硬件安全模块、多签 |
| 智能合约漏洞 | 高 | 审计、形式化验证 |

### 7.2 合规风险

| 风险 | 说明 |
|------|------|
| KYC/AML 要求 | 需要完善的身份验证体系 |
| 跨境监管 | 不同国家对加密支付态度不一 |
| 税务合规 | 自动交易增加税务复杂度 |
| 消费者保护 | 退款、争议处理机制 |

### 7.3 运营风险

- **资金不可逆性**：区块链转账无法撤回
- **Agent 失控**：长期运行的 Agent 可能出现上下文漂移
- **系统依赖**：过度依赖单一平台（Stripe）

## 八、关键结论

### 8.1 郭宇观点的核心价值

3. **从建议到执行**：Agent 不再只是参谋，而是可以执行资金操作
