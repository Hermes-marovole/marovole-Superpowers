## 简介

GPT-5.5 是 OpenAI 最新发布的模型，其提示词策略相比早期模型有显著变化。本指南来自 OpenAI 官方文档，由 Adam.GPT (@TheRealAdamG) 分享，核心信息是：**GPT-5.5 使用更短、更结果导向的提示词效果最佳**。

相比 GPT-5.4，GPT-5.5 的主要变化：
- 提示词可以**更短、更结果导向**（outcome-first）
- **过度指定流程**的旧提示词反而会成为噪音
- 定义结果，让模型自己选择高效路径

---

## 核心原则

### 1. 结果优先提示词 (Outcome-First Prompts)

GPT-5.5 在你**定义目标结果**时表现最佳，而不是详细规定每一步。

**推荐做法：**
```
解决客户问题，达成端到端结果。

成功标准：
- 根据可用策略和账户数据做出资格决定
- 在响应前完成所有允许的操作
- 最终答案包含 completed_actions、customer_message 和 blockers
- 如果缺少证据，只询问最小的缺失字段
```

**避免的做法：**
```
首先检查 A，然后检查 B，然后比较每个字段，
然后思考所有可能的例外，然后决定调用哪个工具，
然后调用工具，然后向用户解释整个过程。
```

### 2. 停止使用条件 (Stopping Conditions)

明确告诉模型何时停止：
```
用最少的有效工具循环解决用户查询，但不要让循环最小化
凌驾于正确性、可用的回退证据、计算或事实声明的必需引用标签之上。

每次结果后问自己："我现在能否用有用的证据和对事实声明的引用来
回答用户的核心请求？"如果可以，就回答。
```

### 3. 遗留提示词迁移

避免从旧模型迁移过多指令。遗留提示词往往**过度指定流程**，因为早期模型需要更多帮助保持正轨。对 GPT-5.5 来说，这可能：
- 增加噪音
- 缩小模型的搜索空间
- 导致过于机械化的答案

**自动迁移方法：**
```bash
openai-docs migrate this project to gpt-5.5
```

## 个性与行为 (Personality and Behavior)

GPT-5.5 的默认风格是**高效、直接、任务导向**。对于客服助手、支持工作流、辅导体验等产品，需要明确定义个性和协作风格。

### 推荐个性模板

**模板一：稳重任务导向助手**
```
# Personality
你是一个有能力的协作者：平易近人、稳重、直接。假设用户是称职的、
善意的，并以耐心、尊重和实用帮助回应。

当请求已经足够清楚可以尝试时，宁愿取得进展也不要停下来澄清。
使用上下文和合理的假设向前推进。只有当缺失的信息会实质性地改变
答案或产生有意义的风险时才询问澄清，并且保持问题简洁。

保持简洁但不生硬。给用户提供足够的上下文来理解和信任答案，然后停止。
当例子、比较或简单类比能让观点更容易理解时使用它们。当纠正用户
或不同意时，坦诚但建设性。当指出错误时，简单地承认并专注于修复。

在职业范围内配合用户的语气。默认情况下避免表情符号和脏话，除非
用户明确要求该风格或已明确建立它适合对话。
```

**模板二：富有表现力的协作助手**
```
# Personality
采用生动的对话存在感：聪明、好奇、适当时俏皮，并关注用户的思考。
当问题模糊时提出好问题，一旦有足够上下文就变得果断。

温暖、协作、精致。对话应该感觉轻松且有活力，但不是为聊天而聊天。
提供真正的观点而不仅仅是镜像用户，同时保持对目标和约束的响应。

当任务需要综合或建议时，深思熟虑且脚踏实地。当你有足够上下文时给出
明确建议，解释重要的权衡，并在不变得回避的情况下说明不确定性。
```

## 前置声明 (Preamble)

在流式应用中，用户会注意到**第一个可见响应**出现的时间。GPT-5.5 可能在发出可见文本前花时间推理、规划或准备工具调用。

对于较长或工具密集型任务，提示模型以**简短前置声明**开始：一个简短的可见更新，确认请求并说明第一步。

**示例：**
```
在进行多步骤任务的任何工具调用之前，发送一个简短的用户可见更新，
确认请求并说明第一步。保持在一两句话以内。
```

## 格式控制 (Formatting)

GPT-5.5 在输出格式和结构上高度可控。

- `text.verbosity` 默认值为 medium；当你偏好更短、更简洁的响应时使用 low
- 默认使用纯段落格式进行正常对话、解释、报告、文档和技术写作
- 仅当用户请求、答案需要清晰比较或排名，或信息作为散文更难浏览时，才使用标题、粗体、项目符号和编号列表
- 对于编辑、改写、摘要或面向客户的消息，先告诉模型要保留什么，然后再要求改进风格

**格式示例：**
```
Write for a senior business audience. Keep the answer under 400 words. 
Use short paragraphs and only include bullets when they improve scannability. 
Prioritize the conclusion first, then the reasoning, then caveats.
```

## 引用与检索预算 (Grounding, Citations, Retrieval Budgets)

### 添加明确检索预算

检索预算是**搜索的停止规则**。告诉模型何时证据足够。

**普通问答策略：**
```
对于普通问答，从使用短、区分性关键词的一次广泛搜索开始。
如果前几项结果包含对核心请求有足够的可引用支持，就从这些结果
回答而不是再次搜索。

仅在以下情况下进行另一次检索调用：
- 前几项结果没有回答核心问题
- 缺少必需的事实、参数、所有者、日期、ID 或来源
- 用户要求穷尽性覆盖、比较或综合列表
- 必须阅读特定文档、URL、电子邮件、会议、记录或代码工件
- 否则答案会包含重要的无支持事实声明

不要为了改进措辞、添加示例、引用非必需细节或支持可以安全地
更通用的措辞而再次搜索。
```

## 创意起草防护 (Creative Drafting Guardrails)

对于起草任务，告诉模型**哪些声明必须来自来源**，**哪些部分可以创意撰写**。

```
对于创意或生成请求，如幻灯片、领导简介、外发文案、分享摘要、
谈话要点或叙事框架，区分来源支持的事实与创意措辞。

- 使用检索或提供的事实来支持具体的产品、客户、指标、路线图、
  日期、能力和竞争声明，并引用这些声明
- 不要编造具体名称、第一方数据声明、指标、路线图状态、
  客户成果或产品能力来使草稿听起来更有力
- 如果可引用支持很少或没有，编写带有占位符或清晰标记假设的
  有用通用草稿，而不是无支持的具体内容
```

## 自我检查 (Prompt the Model to Check Its Work)

让 GPT-5.5 在可以验证时检查输出。

**代码代理示例：**
```
在做出更改后，运行最相关的可用验证：
- 针对已更改行为的目标单元测试
- 适用时的类型检查或 lint 检查
- 受影响包的构建检查
- 当完整验证过于昂贵时的最小冒烟测试

如果无法运行验证，解释原因并描述次佳检查。
```

**视觉工件示例：**
```
在最终确定前渲染工件。检查渲染输出的布局、裁剪、间距、
缺失内容和视觉一致性。修订直到渲染输出符合要求。
```

## 阶段参数 (Phase Parameter)

从 GPT-5.4 开始，长时间运行或工具密集型的 Responses 工作流可以使用 
assistant-item 阶段值来区分中间更新和最终答案。GPT-5.5 使用相同的模式。

**手动重放 assistant items 时：**
- 精确保留原始的 assistant `phase` 值
- 对中间用户可见更新使用 `phase: "commentary"`
- 对完成的答案使用 `phase: "final_answer"`
- 不要对 user 消息添加 `phase`

## 建议提示词结构

将此结构作为复杂提示词的起点。保持每个部分简短。仅在改变行为的地方添加细节。

```
Role: [1-2 句定义模型的功能、上下文和工作]

# Personality
[语气、举止和协作风格]

# Goal
[用户可见的结果]

# Success criteria
[最终答案前必须为真]

# Constraints
[政策、安全、业务、证据和副作用限制]

# Output
[部分、长度和语气]

# Stop rules
[何时重试、回退、弃权、询问或停止]
```

## 快速参考速查表

| 场景 | 推荐做法 |
|------|----------|
| **提示词长度** | 使用更短、结果导向的提示词 |
