## 详细内容

### 一、与 Boris Cherny 搭档：80% 心灵感应，20% 各干各的

**核心洞察：**
> Boris 擅长方向感，会说三个月后、六个月后产品应该长什么样，那个最 AGI pilled 的版本是什么。Cat 的角色是把愿景翻译成执行路径。

**关键要点：**
1. **80% mind-meld** - 两人对愿景高度一致
2. **20% 各干各的** - 谁更在意某件事就主导推进
3. 模糊分工看似不正统，但正是因为模糊才能快
4. Cat 花更多时间在跨职能协调（市场、销售、财务、容量等）

**背景补充：**
- Boris Cherny 是 Claude Code 技术负责人，O'Reilly《Programming TypeScript》作者
- 2024 年 9 月加入 Anthropic 后构建了 Claude Code 的第一个终端原型
- AGI pilled = 对 AGI 即将到来持极其乐观甚至狂热的态度（源自 red pilled）

---

### 二、面试几百个 PM 后的发现：大多数人还活在旧世界

**核心洞察：**
> 最好的 AI 产品 PM，能缩短从"有这个想法"到"产品到了用户手里"的时间，并且能定义出产品必须在哪些任务上开箱即用。

**旧世界 vs AI 时代对比：**

| 维度 | 传统 PM | AI 时代 PM |
|------|---------|-----------|
| 规划周期 | 6-12 个月路线图 | 1 周甚至 1 天发布 |
| 核心工作 | 协调多团队路线图对齐 | 缩短想法到用户手中的时间 |
| 代码成本 | 贵，需要精细规划 | AI 加速工程效率，代码变便宜 |
| 成功标准 | 功能互相解锁 | 工程师周末就能把想法送到用户手里 |

### 三、怎么做到一天出一个功能

Cat 讲了**三件事**：

**第一件：设定清晰目标**
- LLM 能力太通用，用户是谁、解决什么问题、核心场景，全都模糊
- 好 PM 能把这些定死：核心用户是企业专业开发者，解决权限提示疲劳，目标是零权限提示
- 目标一旦清楚，就排除掉大量不相关方案

**第二件：research preview 机制**
- 几乎所有功能先以研究预览形式发布
- 明确告诉用户：这是早期产品、只是想法、在收集反馈、可能不会永远支持
- 降低发布门槛，一两周就能推出去

**第三件：evergreen launch room**
- 工程师把准备好的功能发到频道
- 文档 Sarah、产品市场 Alex、开发者关系同事直接跳进来
- 第二天就能完成对外宣传
- **Cat 说得很明确：搭建这套发布流水线，就是 PM 该干的事**

---

### 四、PRD 没死，但活法不同了

**替代 PRD 的两件事：**

1. **每周 metrics readout** - 整个团队一起看数据，深度理解业务各面、关键目标、趋势和驱动因素

2. **team principles** - 包括谁是核心用户、为什么是他们、愿意做什么取舍，让团队每个人都能自己做决策

**PRD 仍然存在的情况：**
- 特别模糊的功能 → 一页纸列目标、理想场景、当前失败模式
- 需要大量基础设施投入的长期项目
- **但大部分功能不需要 PRD**

---

### 五、不是 Mythos 让他们变快的

**核心结论：**
- 他们已经快了好几个季度，Mythos 不是核心原因
- Mythos 很强大，确实在内部使用，但不足以解释速度提升的主要部分
- **更大的原因是流程和团队的期望设定：每个人都觉得自己有权力也有责任把想法在一周内变成现实**

**Mythos 背景：**
- 内部代号 Capybara，2026 年 4 月 7 日以研究预览形式限量发布
- 主要用于 Project Glasswing 网络安全项目
- 3 月 26 日因 CMS 配置错误提前曝光
- Anthropic 称在代码、推理和网络安全方面大幅超越此前所有模型，已发现数千个零日漏洞

---

### 六、源代码泄露：定性为流程失败

**事件回顾：**
- 2026 年 3 月底，Claude Code 完整源代码通过 npm 包泄露

**Cat 的解释：**
- 人为错误：有人用 Claude 写包发布流程更新的 PR
- 经过两层人工审查，但还是漏了
- 已加固流程，确保不会再发生

**关键回应：**
> 被问到"这个人还在 Anthropic 吗？"Cat 回答很干脆：还在。**这是流程失败，最重要的是学习教训、加强防护。**

**泄露的技术细节：**
- 根本原因：Claude Code 使用 Bun 运行时，Bun 默认生成 source map 文件
- .npmignore 中缺少 `*.map` 条目
- 59.8 MB 的 source map 文件被发布到公共 npm 注册表
- 暴露了约 2,000 个文件、512,000 行 TypeScript 源代码
- 44 个未公开的功能标志
- 名为 **KAIROS** 的自主后台 Agent（能让 Claude 在后台持续运行，用户空闲时做"记忆整理"）
- 这是 13 个月内的第二次代码泄露，且发生在 Mythos 模型信息泄露后仅 5 天

### 七、封堵 OpenClaw：容量管理还是生态围墙？

**Cat 的官方解释：**
- Claude 需求量很大，一直在努力扩展基础设施
- 订阅计划不是为第三方产品的使用模式设计的
- 这类产品给系统带来了不成比例的压力
- 最终决定给每个用户随订阅附赠一些额度
- **核心决策：优先保障第一方产品和 API**

> "We did have to make the hard decision that we needed to prioritize our first-party products and our API."

**未回应的争议：**
- 时间线巧合：Anthropic 在 Cowork 推出类似功能后才封堵第三方工具
- OpenClaw 创始人 Peter Steinberger 批评："先复制热门功能到封闭的 harness 里，再把开源锁在门外"
- Boris Cherny 说"是开源的大粉丝"还给 OpenClaw 提交过 PR，举动和政策之间存在温度差
- 经济角度：$200/月的 Max 订阅用户通过 OpenClaw 可能消耗 $1,000-$5,000 的 API 成本

### 八、PM 团队的全貌

Anthropic 约 **30-40 名 PM**，分布在：

| 团队 | 职责 |
|------|------|
| 研究 PM | 收集客户对模型的反馈并推动模型发布 |
| Claude 开发者平台 | 维护 API 和 Managed Agents 等服务 |
| Claude Code | 核心产品 |
| 企业 | 安全控制、成本管控、RBAC 等大企业功能 |
| 增长 | 整个产品套件的增长 |

### 九、角色融合：工程师、PM、设计师的界限在消失

**核心观察：**
- PM 在写代码
- 工程师在做产品决策
- 设计师在做 PM 的活也在提交代码

**两条路可选：**
1. 大量招有产品品味的工程师 ← **Anthropic 选这条**
2. 维持工程师数量不变、多招 PM 来引导

**最高效的模式：**
> 很多工程师完全能独立完成从"在 Twitter 上看到用户反馈"到"周末发布功能"的全流程，**几乎不需要 PM 参与**。

**当代码变得越来越便宜，真正变得更有价值的是决定写什么。**

**团队背景：**
- Cat 之前在 Scale AI 做产品工程师，Dagster Labs 做工程经理，Index Ventures 做风投
- 几乎所有 PM 要么曾是工程师，要么在 Claude Code 上直接写代码
- 设计师也都做过前端工程师

**工程背景的用处：**
- 能判断一件事应该有多难
- 如果很简单，别讨论，花一小时做掉
- 如果很难，提前知道成本，就能更准确排优先级

**最核心能力：**
> "Product taste is still a very rare skill to have, and we'll pretty much hire anyone who we feel has demonstrated this strongly."

### 十、"恰好正确程度的 AGI 信仰"

**最难的技能：**
定义产品一个月后应该长什么样。模型能力会变成什么样？用户行为会如何改变？

> "It is very hard to be the right amount of AGI pilled."

**终极未来 VS 当下：**
- 终极未来：模型极其聪明，一个输入框就能接入任何工具完成任务
- 但为终极版本做产品太容易了
- **难的是搞清楚当前模型的能力边界在哪，怎么在这个边界内榨出最大价值**
- 太 AGI pilled → 忽略眼前用户痛点
- 太保守 → 在下一次模型升级时措手不及

**好 PM 的信号：**
- 能看到用户如何突破现有产品的极限
- 从这些信号里判断方向
- 在模型能力超出或低于预期时灵活调整路线

**Cat 的做法：**
- 花 **30% 的时间**故意把 Cowork 推到极限
- 和模型对话，搞清楚它为什么在某些任务上犯错

### 十一、模型暂时还不懂的东西

**人脑的剩余优势：**
- 常识和情商
- 判断谁是关键利益相关方
- 理解他们之间的关系、偏好
- 选择正确的沟通场合让他们保持在状态里

Cat 相信模型会越来越擅长这些，但目前缺口还在。

### 十二、P0 到 P0000：混乱中怎么保持理智

**Cat 的团队特质：**
- 都是享受混乱的人
- 面对每个挑战都带着笑容
- 如果对任何事情太紧张，就会燃尽

**很有画面感的描述：**
> "周日晚上出了一个 P0（最高优先级事故），周一又来一个 P0，周一下午来了个 P0000，你会想，天啊，我居然还为周日那个 P0 担心过。"

**应对方式：**
1. 承认你能做的事有限
2. 睡好觉才能第二天做好决策
3. 暴力排优先级
4. 允许产品不够完美
5. 有些发布确实不够打磨，但只要不影响核心场景，就接受它，等反馈，下个版本修

### 十三、速度的代价：功能重叠，用户困惑

**最大的代价：产品一致性**

传统做法：
- 仔细规划产品套件里每个产品的关系
- 每个产品的场景
- 它们怎么整合

Anthropic 现状：
- 有时候同时推出功能重叠的东西
- 因为内部有两种方案都不错
- 想让外部用户来告诉他们哪个更好

**代价：**
- 新用户可能不知道完成某件事的最佳路径是什么
- 需要做更多教育工作来帮用户理解核心功能和最佳实践

---

### 十四、Anthropic 为什么能赢：使命和聚焦

**核心因素：统一使命**

> "Anthropic 招的是最在意'把安全 AGI 带给全人类'的人，这个使命在产品决策中被频繁引用。"

**使命的具体含义：**
> "Mission means that teams are willing to make sacrifices that hurt their own goals and their own KRs in service of Anthropic's goals and Anthropic's KRs."

- 使命高于任何单个产品线
- 跨组织决策可以非常快
- 执行可以高度统一
- 团队愿意做出牺牲自身目标和 KR 的决策
- **人们很乐意做这种取舍**

### 十五、Claude Code、Desktop、Cowork：什么时候用哪个

**清晰的分类指南：**

| 产品形态 | 适用场景 | Cat 的使用方式 |
|----------|----------|---------------|
| **CLI 命令行版** | 最强大的，功能通常最先上线。适合随手启动编程任务，需要最新最全功能 | 随手启动编程任务 |
| **Desktop 版** | 适合做前端开发 | 打开预览窗格，一边和 Claude 聊天一边实时看构建的 Web 应用 |
| **Web 和移动端** | 适合不在电脑前的时候 | 走在路上有想法，掏出手机就能启动任务 |
| **Cowork** | 处理非代码输出 | 回完 Slack 消息、做客户会议的 slide deck、写功能目标文档 |

**Cowork 发挥最大作用的前提：**
- 连接所有相关数据源
- Google Calendar、Slack、Gmail、Google Drive
- 只有 Cowork 能访问到足够的上下文，才能给出高质量的输出

### 十六、自定义应用：每个人的个人 SaaS

**案例：销售团队的自动化演示文稿工具**

背景：
- 销售团队有人发现自己反复做同样类型的演示文稿

解决方案：
- 用 Claude Code 做了一个 web 应用
- 内置效果好的 deck 模板
- 从 Salesforce 和 Gong 拉取客户数据
- 自动生成针对特定客户的定制 deck
- 标注客户是用 Bedrock 还是 Claude Code for Enterprise
- 对应不同的功能集

### 十七、Token 花费在涨，但仍低于薪资

**趋势确认：**
- 每次模型升级或产品大幅改进后，人们会把更多任务交给 AI
- 花更多时间在 Claude Code 和 Cowork 里
- 单个工程师或知识工作者的 token 成本确实在增长

**当前状态：**
- 仍远低于工程师薪资
- 只是占比在持续上升

### 十八、Claude 的性格是护城河

**核心差异化：性格**

用户经常提到 Claude 让人觉得"轻松有趣但又极其能干"。

**两个性格特点：**

1. **低 ego**
   - 你告诉 Claude 它做错了
   - 它会："哎呀，谢谢你告诉我，我来修"
   - 而不是辩解

2. **积极正面**
   - 面对看起来无从下手的任务
   - Claude 会说："没关系，我觉得我们可以这样开始，要我先帮你动手吗？"

**类比：**
> 回想你合作过的所有人，总有一些人让你觉得他们的能量特别好。Claude 的目标就是做那种同事。

### 十九、产品愿景：从单任务到 Agent 矩阵

**核心构建单元：**
单个任务的成功率：给一个清晰的 prompt，能不能持续产出可接受的输出？

**演进路线：**

```
单任务成功
    ↓
6 个任务同时做 (2025 年底 multi-coding 大趋势)
    ↓
50 个 Claude 同时跑
    ↓
上百个 Agent 并行
    ↓
Agent 矩阵
```

**从单兵作战走向 Agent 矩阵。**

## 编辑手记：三个值得关注的矛盾

这期访谈整体相当友好，但几个有意思的矛盾值得关注：

**矛盾 1：速度文化与安全承诺的缝隙**
- Cat 大量篇幅讲"一天出一个功能"的速度文化
- 但 Anthropic 是把"安全"写在名片上的 AI 实验室
- 一周内两次信息外泄（Mythos CMS 错配 + Claude Code 源码 source map）
- 解释都是"人为失误，已加防护"
- 对速度文化本身是否加剧风险，没有任何反思

**矛盾 2：开放生态与围墙花园的取舍**
- Cat 对 OpenClaw 的解释在经济逻辑上成立
- 但时间线巧合：Anthropic 在 Cowork 推出类似功能后才封堵第三方
- Peter Steinberger 批评"先复制热门功能到封闭 harness，再把开源锁在门外"
- Boris 说"是开源的大粉丝"还给 OpenClaw 提交 PR
- 举动和政策之间的温度差，比政策本身更值得玩味

**矛盾 3：PM 角色的悖论**
- Cat 用"角色融合"描述 PM 的未来
- 但最高效模式是工程师端到端完成全流程，"几乎不需要 PM 参与"
- 如果这是真的，PM 的价值到底在哪？
- Cat 答案是 product taste，但整场对话中始终停留在抽象层面
- 没有给出可操作的定义或评估标准
- 筛选标准无法被明确描述时，容易变成不可证伪的门槛
- 关于 AGI pilled 的论述暗含更深悖论：如果模型足够强，一个文本框就够了
- **一个产品负责人承认自己的工作有保质期，这种坦率不常见**
