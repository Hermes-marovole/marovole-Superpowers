## 1. Claude Code 入门：克服终端恐惧

### 1.1 核心转变：从"搬运"到"直接执行"

传统 AI 对话工具（如豆包）的工作流：
1. 你描述需求
2. AI 生成代码
3. **你复制粘贴到别处测试**

Claude Code 的工作流：
1. 你描述需求
2. AI **直接在终端运行代码**
3. 省去搬运步骤

**关键心态转变**：把执行权交给 AI，而不是自己来回搬运。

### 1.2 终端入门：推荐 Termius

对于没用过终端的同学，推荐 [Termius](https://termius.com/) —— 专为 AI Coding 优化的终端：

- ✅ 装好即用，无需折腾配色和字体
- ✅ 深色/浅色跟随系统
- ✅ 分屏：`Cmd + D`
- ✅ 文件管理器：`Cmd + Shift + Y`
- ✅ 内置 AI 辅助：
  - 命令报错自动给修复建议
  - 记不住命令时在前面加 `#` 写中文也能生成

### 1.3 安装 Claude Code

```bash
curl -fsSL https://claude.ai/install | bash
```

进入项目文件夹，输入 `claude` 即可开始。

## 2. 非技术人员需要了解的基础概念

不需要学到能自己写代码的程度，但了解这些概念能大幅提升协作效率：

### 2.1 常用框架是干嘛的

知道 React、Vue、Next.js 大概在解决什么问题，看 AI 写出来的东西不会一头雾水。

### 2.2 常用软件基础

- 终端命令
- Git（版本控制）
- VS Code（编辑器）
- Chrome 开发者工具

跑出错的时候你能跟着定位，而不是只能干等。

### 2.3 编程核心思想

- **函数**：干什么的
- **变量和状态**：存什么数据
- **文件拆分**：为什么要分成多个文件

懂了这些，需求才能写得精确。

### 2.4 学会读代码和读报错

**比会写代码更早派上用场的能力**：
- AI 改完代码，你能扫一眼知道大概在干嘛
- 报错别慌，整段复制丢回去问"这是什么意思、要怎么改"
- 十次有九次能告诉你具体哪一行出问题

### 2.5 推荐入门资源

花一两个晚上过一遍：
- [freeCodeCamp](https://www.freecodecamp.org/)
- [MDN 入门篇](https://developer.mozilla.org/)
- B 站入门课程

### 2.6 推荐三本工程师入门书

| 书名 | 重点 |
|------|------|
| 《黑客与画家》 | 产品判断 |
| 《Unix 编程艺术》 | 工程哲学 |
| 《左耳朵耗子》 | 程序员专家视野 |

读完跟 AI 聊技术细节会少懵很多。

## 4. Claude Code 的核心优势

### 4.1 与其他工具对比

| 工具 | 特点 |
|------|------|
| Cursor | IDE 集成 |
| Windsurf | 协作式编辑 |
| Codex | OpenAI 官方 |
| **Claude Code** | **终端原生 + 模型能力强 + 自主执行** |

### 4.2 为什么主力选 Claude Code

1. **模型能力本身优秀**
2. **代码实现把 Agent 能力发挥到极致**：
   - 先扫 `CLAUDE.md` 和目录结构摸清楚上下文
   - 跨文件改代码、跑命令、看报错、再改 —— 自己全部完成
3. **活在终端里**：git、测试、脚本等日常工具直接调用，不用来回复制粘贴

### 4.3 不只是写代码工具

Anthropic 内部非工程团队（销售、风控、财务）都在用 Claude Code 处理 CRM 数据和客户邮件。

**桌面替代方案**：Cowork
- 不想碰终端可用
- 直接读写下载和文档目录
- 例如：把收据截图拼成报销表

### 4.4 核心原则：准比快重要

> 模型快不快不重要，准不准才重要。

它 10 分钟跑完然后你花 20 分钟 debug，远不如它 20 分钟跑完直接能验收。

**前提**：给到的活本身就要「目标清楚、结果好验收」。

## 6. 循序渐进的上手路径

**核心概念**：Software for One（只给你一个人用的软件）

> 《纽约时报》专栏作家 Kevin Roose 的观点：你不需要做给一百万人用的 App，可以做只给你一个人用的软件。

### 6.1 建议实践节奏

| 时间 | 任务 | 产出 |
|------|------|------|
| **第 1 天** | 试水 | 让它改一个手头现成的 Excel 或 Markdown 文档 |
| **第 1 周** | 尝鲜 | 做一个单页个人主页或日报大盘（15 分钟就能跑起来） |
| **第 1 个月** | 提效 | 挑一件每周重复做两三次的事，变成一条命令或一个页面 |
| **第 3 个月** | 进阶 | 选一个 "software for one" 的想法，做一个只给自己用的小工具 |

### 6.2 示例

- 整理链接的 Stash
- 给孩子准备便当的 LunchBox Buddy
- 把语音批注转成会议纪要的工具
- 每天提醒你三件事的小仪表盘

**产品/业务/运营同学的优势**：最懂自己每天的麻烦在哪。

## 7. 浏览器自动化与 OpenCLI

很多运营日常工作是在浏览器里点点点：查后台、发消息、导报表。这些活可以绕开界面，直接调背后的接口。

### 7.1 OpenCLI 介绍

[OpenCLI](https://github.com/piglei/opencli) —— 内置了小红书、知乎、Twitter/X、Bilibili 等几十个站点的 CLI 适配器，再加上浏览器操作原语（点击、输入、抓取、截图）。

### 7.2 实战场景

**小红书调研**
```bash
# 让 Claude Code 调 opencli xiaohongshu 抓数据
# 再做分类和热词提炼
# 原本浏览器里点半天的事，一句话搞定
```

**舆情汇总**
```bash
# 把 Twitter/X、Reddit、HackerNews 几个适配器组合
# 同一关键词在多个平台的讨论自动拼成日报
```

**没适配的网站**
```bash
# 用浏览器原语描述流程
# 开页面 → 输关键词 → 抓表格
# Claude Code 自己拼出来
```

## 9. CLAUDE.md：项目级记忆配置

### 9.1 为什么重要

很多人装好后直接开问，结果每次都要重复交代背景，用一会就觉得很烦。

**原因**：没建 `CLAUDE.md`。

### 9.2 是什么

- 放在项目根目录
- Claude Code 每次启动都会先读它
- 相当于给新同事写的项目交接文档
- **区别**：它每次都会从头认真读一遍，而且严格执行

### 9.3 写好 CLAUDE.md 的三要素

1. **写得短一点**：150 行以内为佳，太长会挤压后续对话空间
2. **语气直接，用命令式**：
   - ❌ "我们团队比较喜欢中文注释"
   - ✅ "所有注释用中文"
3. **每条都能判断**：
   - ❌ "代码质量要高"
   - ✅ "函数超过 50 行必须拆分"

### 9.4 四条最值钱的规则

| 规则 | 展开说明 |
|------|----------|
| **先问清楚再动手** | 别让它猜你的意图，目标说清再写 |
| **简单优先** | 能两行解决的不写两百行，拒绝过度设计 |
| **只动该动的** | 不要顺手重构没让它改的代码 |
| **做完要验证** | 跑通构建和测试才算完，没通过别说完成 |

### 9.5 模板示例

```markdown
# 项目背景
这是一个面向运营同学的客户看板，技术栈 Node.js + Next.js，
前端用 React，数据库 PostgreSQL，部署在 Vercel。
产品经理是 Alice，设计是 Bob，后端是我自己。

# 工作规范
- 所有注释用中文，变量函数用英文。
- 改动前先说明你打算改什么，确认后再动手。
- 新功能先写实现，不主动加测试，除非我明确要求。
- 数据库表名用下划线分隔，比如 user_profile。

# 禁止项
- 不要主动重构我没提到的文件。
- 不要删除任何文件，除非我明确说删掉。
- 不要在没确认前直接执行 npm install 装新依赖。

# 压缩时保留
长对话被自动压缩时，按优先级保留：
1. 架构决策和它背后的理由
2. 改过哪些文件、改了什么
3. 当前进展状态
4. 还没做完的 TODO
```

**最后一段很重要**：长会话压缩时会丢掉决策理由，导致前后矛盾。把这一段写进去，能保住关键上下文。

### 9.6 自动生成

装好 Claude Code 后，直接说：
> "读一下我这个项目，帮我生成一份 CLAUDE.md"

它会扫代码、技术栈、目录结构，给你一份草稿，你改改人名和团队偏好就行。

## 10. 需求描述的精确 vs 模糊

### 10.1 对比示例

**模糊版**：
> "帮我做一个客户跟进工具"

**精确版**：
> "帮我做个销售用的跟进工具，单文件网页存本地。左边列表显示公司名、下次跟进时间、状态，右边详情包括沟通记录、日期、要点。顶部加三个筛选：状态、时间、关键词。数据存浏览器 localStorage，不调后端。"

**结果**：精确版当天就能跑出能用的版本，模糊版多半要返工。

### 10.2 完整精确需求示例

这是 yetone 给 Claude Code 写的 macOS 语音输入工具需求（节选）：

```markdown
帮我做一个 macOS 原生语音输入工具，用 Swift 开发：

1. 按住 Fn 键开始录音，松开后把转录文字注入当前光标所在的输入框。
   优先用流式转录（Apple Speech Recognition framework）。
   Fn 键通过 CGEvent tap 全局监听，需抑制 Fn 事件传递，
   避免触发 emoji 选择器。

2. 默认语言必须为简体中文（zh-CN），开箱即用就能识别中文。
   菜单栏可切换英文、繁中、日语、韩语，选项存到 UserDefaults。

3. 录音时屏幕底部居中显示一个无边框胶囊状悬浮窗：
   不要红绿灯和 titlebar，用 NSPanel（nonactivatingPanel）+
   NSVisualEffectView（.hudWindow 材质）。
   高度 56px，圆角 28px，左侧实时音频波形（5 根竖条，
   由 RMS 电平驱动），右侧转录文字（160-560px 弹性宽度）。
   入场弹簧动画 0.35s，文字宽度过渡 0.25s，退场缩放动画 0.22s。

4. 文字注入用剪贴板 + 模拟 Cmd+V。注入前检测当前输入法：
   如果是 CJK 输入法，先临时切到 ABC 键盘再粘贴，完成后恢复原输入法。
   注入完恢复原剪贴板内容。

5. 接入 LLM 提升识别准确率，处理中英文混杂场景。
   通过 OpenAI 兼容 API（可配置 Base URL、Key、Model）对转录文本做 refine。
   system prompt 要求极保守：只修复明显的语音识别错误
   （如"配森"→"Python"、"杰森"→"JSON"），
   绝不改写或润色看起来正确的内容，正确就原样返回。
```

**关键洞察**：你不需要会写 Swift，但需要把需求写得这么细。每条背后都是踩过的坑或预想到的坑。**每多一条具体细节，就少一次返工**。

### 10.3 业务场景需求写作框架

**开头先把问题写清楚**：
- 要解决什么
- 给谁用
- 怎么算做对了

**示例**：
> "国际门票目前没有独立入口，用户只能搜索找到，非热门城市曝光极低"

这两句话决定了后面碰到"热门城市展示几个""筛选要不要做'最近浏览'"时的判断方向。

**划范围**：
> "不做登录态、不做分享、不做 SEO，下一期再说"

Claude Code 很积极，不划范围会顺手加收藏、分享、埋点。

**异常情况单独列**：
- 接口超时怎么办
- 数据为空展示什么
- 图片挂了用什么兜底

**验收标准给数字**：
- ❌ "页面要快"
- ✅ "首屏 1.5 秒内"

- ❌ "布局正常"
- ✅ "在 375 和 1440 两个宽度下不错位"

**别用模糊词**：
- ❌ "待定""后续再看""TBD"
- ✅ "这一版先硬编码，下版再做配置化"

## 11. Plan 模式：先规划再执行

### 11.1 为什么用 Plan 模式

直接开搞的风险：
- 复杂任务让 AI 顺手删了后面要用的文件
- 回滚花半小时

**解决方案**：复杂任务先按两次 `Shift+Tab` 切到 Plan 模式。

### 11.2 Plan 模式产出

- 要改哪几个文件
- 每个文件改什么
- 改的理由是什么
- 预计会影响哪些地方

**判断标准**：用业务逻辑判断方向对不对，比判断代码本身容易得多。

### 11.3 Auto 模式

按 `Shift+Tab` 循环切换：
- **Plan** → **Auto** → **默认**

Auto 模式逻辑：
- 读文件等安全操作 → 直接跑
- 改数据库、删文件等风险操作 → 来问你

**建议**：刚上手默认开 Auto 模式，既不会被无意义的确认打断，也不会让它瞎搞。

## 12. 版本控制与撤销策略

### 12.1 Git 快照

每次大改前让它先跑 `git status` 看清楚都有什么，确认没问题再 commit 一个检查点。

**回退**：
> "按刚才的检查点回退"

比自己手动 checkout 安全得多。

### 12.2 撤销上一步

> "撤销刚才所有改动"

或按 `/rewind` 回到上一个状态。

### 12.3 避免「改了试试」循环

**坑**：4-5 轮下来，本来不大的问题变成一团乱麻。

**原因**：没诊断清楚就开始打补丁。

**解决方法**：
> 根因没说清楚之前先别动代码。

让它先答：
> "问题出在哪个文件的哪一行，为什么会这样"

答含糊继续查，答清楚再改。

**喊停信号**：一上来说"我试试改 X 看行不行"的，直接喊停让它先答根因。

## 13. 进阶配置与效率技巧

### 13.1 alias 快捷启动

在 `.zshrc` 里加：

```bash
alias c='CLAUDE_CODE_AUTO_COMPACT_WINDOW=400000 claude --dangerously-skip-permissions'
```

**作用**：
- 按 `c` 直接启动不再问权限的 Claude Code
- 自动压缩点提前到 400k（上下文塞满前压缩，效果更好）

**⚠️ 警告**：`--dangerously-skip-permissions` 字面意思就是"危险跳过所有权限确认"，不会再问你任何事。只有能看懂它每一步在做什么的人才建议用。没到这个程度，老老实实用 Auto 模式。

### 13.2 模型切换

输入隐藏命令：
```
/model opusplan
```

**逻辑**：
- 规划交给 Opus
- 执行交给 Sonnet
- 整体省钱省时间

更快可再跑 `/fast`

### 13.3 关键配置

如果支持，在 `~/.claude/settings.json` 里设置：

```json
{
  "showClearContextOnPlanAccept": true
}
```

**原因**：用 opusplan 时，不开这个会在 Sonnet 段碰到严重的缓存未命中，速度明显慢下来。

### 13.4 会话管理

Claude Code 工作台固定大小，跑久了早期内容会被挤出去。

**策略**：
- 任务做完就 `/clear`
- 一个会话只做一件事
- 做完清掉再开下一件
- 两件不相干的事在同一个上下文里来回切，会越做越乱

**长任务交接**：
> "把当前进度写成一份 HANDOFF.md，包括做了什么、试过什么没成功、下一步该做什么。"

第二天打开新会话，把文件给它，就能接着干，不依赖任何压缩算法。

## 14. Skills：沉淀工作习惯

### 14.1 什么是 Skill

Skill 本质就是一个文件夹，放在 `.claude/skills/` 目录下：
- 里面有 `SKILL.md` 写清楚什么时候用、要做什么
- Claude Code 启动时只读 frontmatter（约 100 字的触发条件）
- 真正调用时才加载完整内容
- **优势**：装几十个 Skill 启动也不会变慢

### 14.2 Tw93 的 8 个 Skills

| Skill | 作用 |
|-------|------|
| `/think` | 动手前先想技术方案，质疑问题本身、思考好方案再跑 |
| `/design` | 帮你设计产品化页面，拒绝蓝紫渐变+emoji 的 AI 模板感 |
| `/debug` | 排查问题，根因没说清楚之前先别动代码 |
| `/review` | 收工前最后检查，diff 审一遍，自动修的修掉，拿不准的归拢起来再问你 |
| `/read` | 把任意网页或 PDF 转成干净 Markdown 进工作流 |
| `/write` | 让你的表达更清晰 |
| `/learn` | 从收资料到出文章的研究流程 |
| `/health` | 给 CLAUDE.md 和各种规则做体检，感觉 Claude 不好用时运行 |

**最推荐非技术人员先试**：`/design`

截图丢给它带上 `/design`，它会先反问：
- 给谁用
- 想要什么气质
- 最不喜欢哪种风格
- 有没有想让用户记住的微交互

回答完再动手，效果比直接说"帮我改一下样式"稳定。

### 14.3 三种 Skill 类型

#### 类型 1：工作流型

把每次都要做的固定步骤打包。

**示例：整理周会纪要**

```markdown
---
name: 整理周会
description: 开完会有原始记录需要整理时调用
---

## 输出格式
**本周达成**：[负责人] 完成了什么
**下周计划**：[负责人] 做什么，截止时间
**待讨论**：卡在哪里，需要谁来决定
**行动项**：[谁] [做什么] [什么时候]

## 规则
- 不润色，保持原始措辞
- 信息缺失就标注"待确认"，不要猜
```

#### 类型 2：检查清单型

上线前、发版前、提交前过一遍，避免漏项。

**示例：需求上线检查**

```markdown
---
name: 需求上线检查
description: 需求发布前跑一遍，确认没有遗漏
---

## 上线前必须全部通过
- [ ] PRD 里的验收标准逐条确认
- [ ] 设计稿和实现对齐，间距、文案、交互没漏
- [ ] 异常状态（空态、报错、超时）都有处理
- [ ] 数据埋点按规范打好
- [ ] 测试环境验证通过

## 输出
每项 Pass / Fail，有 Fail 必须修完再发布。
```

#### 类型 3：领域专家型

把判断框架沉淀进去，碰到这类问题按固定路径走，不让它每次自由发挥。

**示例：线上问题排查**

```markdown
---
name: 线上问题排查
description: 收到线上告警或用户反馈异常时调用
---

## 收集信息
- 报错截图或错误日志的完整内容
- 影响范围：哪些用户、哪个页面、什么时间开始
- 最近的变更：代码发布、配置修改、数据变更

## 判断矩阵

| 现象| 优先检查 |
| 页面白屏 | JS 报错 → 最近发布记录    |
| 接口超时 | 服务监控 → 数据库慢查询    |
| 数据异常 | 最近数据变更 → 上下游依赖  |

## 输出格式
根因 / 影响范围 / 修复步骤 / 验证方式
```

### 14.4 写 Skill 的两个坑

1. **description 写触发条件，不写功能介绍**
   - ❌ "把会议录音整理成结构化周报"
   - ✅ "开完会有原始记录需要整理时调用"

2. **一个 Skill 只做一件事**
   - ❌ 把审查、发布、调试塞在一起
   - ✅ 拆开用起来才更准

## 15. AI 排版与原型工具

### 15.1 Kami：AI 排版设计工具

[Kami](https://kami-ui.com/) —— 把内容丢给它，说一句"帮我排成一页纸"或"做个作品集"，生成可下载的 PDF。

**8 套模板**：
- 一页纸
- 作品集
- 幻灯片
- Resume
- 长文档
- 信件
- 研报
- Changelog

**风格统一**：
- 暖底色
- 墨蓝色点缀
- 衬线字体为主
- 中文：苍耳今楷
- 英文：Charter

**实用场景**：
- 会议纪要排成简报
- 项目进展排成一页纸给老板

以前开 Word 或 Figma 折腾半天，现在把内容丢进去，先出一版能看的稿子，再微调。

### 15.2 Vibe Coding：截图/文档转原型

2026 年 4 月推出的 [Vibe Coding](https://vibecoding.ai) —— 上传截图或文档，直接给你个能交互的原型、幻灯片或落地页。

**适用人群**：想快速做原型的非技术同学。

**产品经理用法**：
1. 用它画原型开评审
2. 过了直接把原型扔给 Claude Code 变代码
3. 早期原型不用等完整设计和研发排期，当天就能拿出来讨论

## 16. 实用技巧与避坑指南

### 16.1 截图比文字快

要描述界面问题或想参考某个设计风格，**直接丢图**比写一段话准多了：
- 布局
- 颜色
- 层级

全都带进来了，让 AI 少猜。

### 16.2 任务拆小一件件来

一句话能讲清楚的任务，AI 几乎不会出错。

一上来给一大坨需求，它中间任意一步走偏，后面就全偏了。**一件做完验收一件再开下一件**。

### 16.3 对话跑偏就重启

在已经跑偏的对话里来回纠正，它越纠越乱。**清掉上下文重说一遍需求往往更快**。

第二天接着干，先翻一眼上次的 Recap（`/clear` 后自动生成的会话摘要），想起来干到哪了。

### 16.4 Memory 跨项目记住偏好

- **CLAUDE.md**：项目级，每个项目单独写
- **Memory**：用户级，跨所有项目和会话生效

直接说：
> "记住我喜欢先看方案再执行"
> "记住回我中文"

它会写进 `~/.claude/memory/`，以后任何项目打开都记得。

**常交代的背景信息**都可以沉淀进去，省得每次重复说。

### 16.5 双击 ESC 改上一条

说错了或者它跑偏了，**按两下 ESC** 就能回到上一条消息修改，不用重开会话。

### 16.6 让它先解释再动手

在 `CLAUDE.md` 里加一条：
> "每次执行 Bash 命令或修改文件前，先用一句话解释要做什么。"

它就会在每步操作前先告诉你打算干嘛。看不懂代码没关系，看得懂"我要删掉这个文件"就够了。

### 16.7 看不懂的命令先问

它要跑一条你没见过的命令别直接放行，先问：
> "这条命令具体做了什么、有什么风险"

看懂了再点确认。**不要复制任何你不懂的命令去执行**，里面可能夹带下载、上传或泄露信息的操作。

### 16.8 生产环境不要拿来练手

本地和测试环境随便折腾，但**涉及生产数据库、线上配置的操作**，一定先在测试环境验证。

一条写错的 SQL 或一次误删，回滚成本远高于你预期。

### 16.9 密钥别直接粘到对话里

要配置 API Key、数据库密码这类东西，让它放到环境变量或者 `.env` 文件里，**不要直接把明文贴到聊天窗口**。

### 16.10 能跑不代表安全

AI 生成的代码可能有漏洞，**涉及登录、支付和个人信息的功能**：
- 能用 Clerk 或 Stripe 这种现成服务
- 就别让它从零写
